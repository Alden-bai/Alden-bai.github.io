# Agent部分

## 一、如何定义 Agent，它和普通的大模型调用有什么区别

easy，回答agent：llm，工具，状态，agent loop

感知环境，调用工具，状态管理，多轮执行

普通的大模型调用：利用不了工具。你让他做什么事情，他会告诉你怎么做，而不是帮你做。但是agent是帮你做

## 二、Function Calling 的完整执行链路是什么

> 用户请求 → 构造 messages 和 tools → LLM 判断是否调用工具 → 返回 tool name 和 arguments → 业务侧校验并执行工具 → 将 tool result 写回上下文 → 再次调用 LLM → LLM 判断继续调用工具还是直接返回最终结果。

前置定义：
shcema：理解为数据的约束说明

JSON shcema：用JSON格式写出来的Schema

arguments： 调用函数时传进去的具体参数值

**重要提醒**：arguments是llm返回，schema是客户端一侧传递给大模型

## 三、工具调用重复执行并陷入死循环应该如何处理

三重机制

1. 调用去重：每次TOOL CALL都记录tool_name + arguments，生成调用指纹，如果多吃出现相同工具相同参数，认为agent没有进展，直接阻断
2. 状态+终止判断：判断任务有没有推进，如果多轮observation基本一致，那么触发终止，返回明确的错误信息，让模型换策略
3. 兜底机制：设置agent loop的最大轮数，tool工具调用的最大次数

## 四、Coding Agent 在执行过程中如何支持用户中途打断

> 用户按 Esc / Ctrl+C / 输入新指令
> → UI 发出 cancel
> → 取消当前 Agent Task
> → 取消信号沿 Agent Loop 向下传播
> → 停止模型流式请求和未完成的工具调用
> → 清理 streaming 状态
> → 保留已经完成的状态
> → 用户可以继续发起下一轮任务。

重要的提醒：

1. 取消不等于回滚，已经修改了的文件不会自动撤销
2. 工具本身也要支持取消
3. 异步取消，输入中止指令了之后，不立马进行阻塞

## 五、上下文压缩设计

Agent 的上下文压缩一般分两层。

第一层是 Tool Result Externalization。对于代码搜索、日志、大文件读取这种大型工具结果，不全部 inline 到 Context，而是把原始结果写入文件或者 Artifact Store，Context 中只保留摘要、关键片段和引用。同时尽量保持已经进入上下文的重要历史 Prefix 不变，避免频繁改写历史影响 Prompt Cache，新产生的大结果优先外置。

第二层是 Global Compaction。当多轮 Agent Loop 导致整个 Conversation 接近 Context Window 时，对历史做一次全局压缩。这个压缩不是平均压缩，而是不对称压缩：优先保留用户目标、明确约束、重要决策、当前文件状态、未完成任务和最近几轮上下文；对于已经完成的 Assistant 中间过程和大型 Tool Result 可以强压缩，Tool Result 原文则通过引用保存在外部。

另外压缩不能等 Context Window 用满才触发，我会提前预留 Summary 输出、下一轮模型输出、Tool Result 和 Safety Margin，所以触发阈值大致是：

Context Window - Summary Budget - Output Budget - Tool Budget - Safety Margin。

整体就是：

1. 大工具调用结果放入磁盘
2. 多次小工具调用，需要stable prefix
3. 全量压缩时需要注意：不对称压缩（区分不同消息的重要性），达到软阈值就进行压缩（提前留出摘要容量和单次工具调用的容量）

## 六、Agent的四层触发机制

触发类型主要分为四种触发：

1. 用户触发（用户显示请求）：用户发送消息进行显示请求
2. 模型触发(模型判断需要行动）：agent把工具schema发送给大模型，大模型返回tool_use，触发列入文件读取，bash命令，ToolSearch这些
3. 事件触发（hook这些，规则/事件）：如生命周期的hook
4. 异步触发（外部状态改变，主要是外部事件驱动）：子agent任务完成后返回

## 七、解释一下什么是mcp

easy题目

MCP，全称是 Model Context Protocol，可以理解成大模型应用和外部能力之间的一套标准协议。

它主要解决的问题是：以前每接一个工具、数据库、文件系统或者第三方服务，都要单独写一套适配代码；MCP 把这些外部能力统一抽象出来，让 Agent 或 LLM Client 可以通过标准接口去发现和调用。

主要核心包括：

1. Tools：模型可以调用的动作
2. Resources：模型可以读取的数据资源
3. Prompts：可复用的提示模板
4. Transport：客户端与服务端之间的通信方式

## 九、权限校验设计怎么做，为什么不能把权限规则写进prompt里面

权限校验主要防止三种情况：

1，prompt注入

2，越权操作

3，数据泄露

权限校验我这里加了五层

第一层：危险命令拦截，有些命令就是不应该被执行的，如rm -rf /

第二层：路径沙箱：所有的文件操作必须限制在项目目录内（允许项目根目录和系统临时目录）

> 有些工具操作，需要访问临时目录

第三层：权限规则

> 细细粒度进行匹配：
>
> 例如bash提取command，readfile提取path，然后进行匹配，看是否允许，返回allow，deny，unknown

第四层：权限模式

>类似于codex的一些模式：请求批准，帮我批准，完全访问这些
>
>**plan模式是只允许只读**

第五层：HITL

> 最后一层，human in the loop，不确定的直接返回给用户，让用户确定，如果以后遇到类似的这种命令，记住用户操作，本次会话自动允许

prompt只能告诉模型怎么做，而不是真正阻止工具的执行。而且prompt也有注入攻击

## 十、Agent中harness概念，什么是harness

Agent = 模型+harness

一个浅显的比喻：llm相当于cpu，上下文窗口相当于RAM，临时存东西但是断电就无了，Harness则是操作系统，管调度，管权限，管理io

harness具体包含：

1. 知识库（CLAUDE.md 这些项目指令文件）
2. 工具集成（MCP、CLI）
3. 权限约束（allow/deny 规则、沙箱）
4. 自动验证（CI、lint、测试）
5. 反馈回路（错误信号返回 Agent 让它自我修正）
6. 状态管理（跨会话的持久化）。

LLM的行为是概率性的，所以Harness必须通过确定性工程机制来兜底概率性行为

最能体现 Harness 思想的是权限系统，反馈回路告诉LLM为什么会错，而不是简单的说失败了，最后就是记忆系统，长短期记忆是怎么设计的，怎么记住用户偏好这些

## 十一、长程任务延迟分析

如：Agent 长程任务平时 5 分钟完成，这次跑了 15～20 分钟

两个出发点分析：单步变慢，还是步数太多了

总耗时异常 → 看 Loop 次数 → 看单步耗时 → 看 retry/重复调用 → 看 Context/Token → 定位根因

重点指标

- agent loop次数
- LLM调用耗时
- Tool执行耗时
- 是否有大量重复的Tool调用还有retry

> 1.  Agent 只需要 10 轮，这次跑了 40 轮，那说明不是单步慢，而是决策效率下降，可能出现重复规划、死循环或者错误恢复
> 2.  Loop 次数正常，但某个 Bash、搜索、数据库或者 MCP Tool 从平时 2 秒变成 30 秒，那就继续下钻 Tool 层，看外部依赖、网络、进程或者服务是否变慢
> 3.  Tool 正常，而 LLM 调用明显变慢，我会继续看输入 Token、输出 Token、上下文长度，以及模型服务本身的 latency

# RAG部分

## 一、什么是RAG，描述一下RAG的工作流程

检索增强，因为大模型训练好了之后，知识就固定了，训练数据截止日之后的知识不知道，遇到最新的知识和信息就答不上来，所以通过RAG，也就是在生成答案之前，在向量数据库里面进行检索，将检索的到的答案和用户的问题一起交给llm，LLM将根据这个上下文进行回答，不用再靠死记硬背了

## 二、大模型的RAG主要是用来解决什么问题的

主要是解决3个问题：

- 大模型幻觉

  > LLM一旦遇到了知识缺失，就会乱回答，自己编一个自己认为正确的答案

- 知识的时效性

  > 第一题上面讲了，LLM在训练了之后，知识就被冻结住了，训练截止之后的事情大模型是不知道的

- 私有知识覆盖

  > 公司的一些内部文档和行业的专有数据是没有办法进入训练集的，所以LLM对于这方面是完全的空白

## 三、相比微调，RAG解决的问题，同时讲讲微调和RAG各自的优势

微调和 RAG 解决的问题其实不太一样。简单来说，**微调主要解决“模型怎么回答”，RAG 主要解决“模型依据什么知识回答”**。

微调会通过训练数据调整模型参数，让模型学习特定的任务能力、回答风格、输出格式或者领域行为。它的优势是这些能力直接体现在模型本身，不需要每次请求都额外检索；但是缺点也比较明显，训练需要一定的时间和计算成本，而且知识一旦发生变化，重新更新模型比较麻烦，所以不适合频繁变化的业务知识。

RAG 不修改大模型参数，而是在模型外部维护一个知识库。用户提问以后，先从知识库检索相关的 Chunk，再把用户问题和检索结果一起交给大模型，让模型基于这些内容生成答案。因此新增或者修改知识时，通常只需要更新知识库，不需要重新训练模型，成本更低，也更适合企业文档、产品资料、规章制度这类经常更新的数据。

另外，RAG 还有一个比较重要的优势是**可溯源**。检索出来的 Chunk 可以携带 `chunk_id`、文档名称、页码等来源信息。如果最终回答错误，可以进一步排查到底是检索阶段没有找到正确内容，还是检索内容正确但大模型生成出了问题。

所以实际应用中，两者并不是互相替代的关系：**需要模型学习特定行为和任务能力时用微调；需要补充最新、私有、可更新、可溯源的知识时，更适合使用 RAG。**

## 四、RAG中的文档存储方式，粒度怎么划分，文档切割的一些策略

三个问题：

- 文档的存储方式
- 粒度怎么划分（太小？太大？）
- 文档切割方式

一个一个解答：

### 1. 文档的存储方式

文档的存储方式主要存 3 个东西，第一个是一个 chunk 块的向量化，一段文本会经过 Embedding 模型，变成一段向量。实际上用户问问题的时候，问题也会被转化为一段向量，然后**通过向量相似度进行匹配，例如余弦相似度。实际的向量数据库还可能使用点积、欧氏距离等方式进行相似度计算。**

第二个是真实的文本，因为 chunk 块的向量化只是为了方便快速检索，有点像操作系统的目录那些底层知识，根据目录把块调进来，真实的数据都在文本当中。检索到对应的 chunk 之后，会将真实文本一同输入进 LLM，LLM 根据检索到的内容和提示词进行回答。

第三个就是 metadata，元数据，有点类似于书签，记录这个 chunk 块的 `chunk_id`、`document_id`、页码、标题、URL 等信息，后续方便定位、过滤以及进行答案溯源。

**所以整体可以理解成：**

```
原始文档 → Chunk → Embedding → vector + text + metadata → 向量数据库
```

**这里需要注意，工程上真实文本不一定必须直接存储在向量数据库中，也可以只在向量数据库中保存 `vector + chunk_id + metadata`，然后通过 `chunk_id` 去其他数据库或者对象存储中获取真实文本。**

------

### 2. 粒度怎么划分

chunk 块划分得太大了，**一个 chunk 中可能同时包含多个主题，这样得到的 Embedding 向量就很难准确表示其中某一个局部主题，也就是语义容易被稀释，导致检索精度下降；而且即使这个 chunk 被检索出来，也会给 LLM 带来大量无关内容。**

chunk 块划分得太小，又会丢失上下文信息，比如一个完整的句子或者一段存在上下文关系的内容，被切成了两个 chunk，检索的时候可能只检索到其中一部分，就会导致语义不完整。

所以粒度的划分本质上是在做一个权衡：

**小 Chunk → 检索更加精确，但是上下文容易不完整**

**大 Chunk → 上下文更加完整，但是容易引入噪声，检索精度下降**

所以具体的 chunk 粒度一般需要结合文档类型和文档切割策略确定。

------

### 3. 文档切割策略

常见的切割策略主要包括：固定切分、**递归切分、语义切分、特殊格式切分、父子切分**，另外还有一个 Late Chunking。

#### （1）固定切分

固定切分一般就是选定多大的块，比如按照固定的字符数量或者 Token 数量进行切分。

但是会出现一个问题，也就是语义丢失。固定切分可能会出现一句话被分成两部分的情况。

比如：

```
北航是一个很牛批的学校
```

切分的时候刚好切成：

```
北航是一个 | 很牛批的学校
```

用户问“很牛批的学校是哪一个学校”，那么可能只检索到“很牛批的学校”对应的 chunk，但是这个 chunk 里面已经没有“北航”了，所以就出现了上下文丢失的问题。

这个时候可以引入 **Overlap（重叠）**，也就是相邻 chunk 之间保留一部分重复内容。

例如：

```
Chunk1：[AAAA BBBB]
Chunk2：[BBBB CCCC]
Chunk3：[CCCC DDDD]
```

每个块的开头和上一个块的结尾重叠一部分，这样能够尽可能避免因为切割边界导致的语义信息丢失。

------

#### （2）递归切分

**之前容易把递归切分和语义切分混在一起。维护一个分隔符优先级，比如先按照章节、段落切，如果 chunk 还是太大，再按照句子切，如果还是太大，再按照 Token 或字符切，这种方式严格来说叫 Recursive Chunking，也就是递归切分。**

例如：

```
章节 → 段落 → 句子 → Token/字符
```

这种方式相比于固定长度暴力切分，更容易保留原文天然存在的结构和语义边界。

------

#### （3）语义切分

既然固定切分可能会丢失语义信息，那么按语义切分就能够尽可能保证同一个 chunk 中的内容是在描述同一件事情。

就像我现在正在做这个笔记一样，每一个段落、每一个章节可能就是在描述一件事情，不同段落描述的主题可能不一样，所以按照语义进行切分能够更好地保证 chunk 内部语义的一致性。

**真正的 Semantic Chunking 一般会分析相邻句子之间的语义关系，例如先对句子做 Embedding，然后计算相邻句子的语义相似度。当相邻内容的语义相似度明显下降，也就是主题发生明显变化的时候，就可以把这里作为一个切割点。**

简单理解就是：

```
句子1 → 句子2 → 句子3 ｜句子4 → 句子5
```

如果句子 1、2、3 都是在讨论 RAG，而句子 4 开始讨论微调，那么句子 3 和句子 4 之间就可以作为一个语义切割点。

------

#### （4）特殊格式的划分

对于 Coding 还有表格来说，需要根据它们自己的结构进行切分。

代码的话，需要按照函数、类这些代码结构来进行划分，一般可以按照函数划分，因为一个函数通常是在完成一个相对独立的功能。

**实际工程中还可以通过 AST（Abstract Syntax Tree，抽象语法树）解析代码，然后根据 Class、Function、Method 等代码结构进行切分，而不是直接按照字符数把代码切断。**

然后表格的话，一般可以转换为 Markdown 格式。因为如果对表格中间直接切一刀，很可能会丢失表头信息。

比如有一个：

```
北航帅哥名单
```

下面第一行是表头，后面是我的名字。刚好从表头和数据中间切了一刀，只看我这个名字，可能没听说过我的人不知道我是北航最帅的帅哥。

所以对于表格切分来说，核心就是**尽可能保证每一个 chunk 都带有对应的表头以及必要的上下文信息。表格除了转换成 Markdown，也可以转换成 HTML 或者其他结构化文本，重点不是必须使用 Markdown，而是保留表格结构。**

------

#### （5）父子切分（面试重点）

父子切分是一个比较常见的面试点。

**父子切分的核心不是“给每个 chunk 生成一个浓缩的句子进行检索”，而是把同一段文档同时划分成较大的父 Chunk 和较小的子 Chunk。**

例如：

```
父 Chunk（1000~2000 tokens）
```

↓ 再进行切分

```
子 Chunk1（200~400 tokens）
子 Chunk2（200~400 tokens）
子 Chunk3（200~400 tokens）
```

**真正进行 Embedding 和向量检索的一般是子 Chunk，因为子 Chunk 比较小、主题更加集中，所以检索的时候更加精准。**

当某一个子 Chunk 被检索到以后，可以根据它保存的 `parent_id` 找到对应的父 Chunk，**最终把信息更加完整的父 Chunk 交给大模型。**

所以父子切分解决的其实就是前面提到的 Chunk 粒度矛盾：

**小 Chunk 适合检索，大 Chunk 适合给 LLM 提供完整上下文。**

可以直接记一句：

**小块负责检索，大块负责生成。**

**而“给一个大 Chunk 生成摘要，然后对摘要进行 Embedding 和检索，检索到摘要之后再返回原始 Chunk”的方式也是存在的，但是这种方式更加接近 Summary Index / Multi-vector Retrieval（摘要索引 / 多向量检索），不要和经典的父子切分混在一起。**

------

#### （6）Late Chunking

一般普通的切分方式，是先切分为块，然后将每一个块分别进行 Embedding：

```
文档 → 切 Chunk → 每个 Chunk 分别 Embedding
```

Late Chunking 的核心思路则是**先让 Embedding 模型在完整的长文本上下文中对所有 Token 进行编码，得到带有全文上下文信息的 Token Embedding，然后再根据 Chunk 的边界进行切分，并对每个 Chunk 范围内的 Token Embedding 进行 Mean Pooling 等操作，最终得到每个 Chunk 的向量。**

简单来说可以记成：

**普通 Chunking：先分块，再 Embedding**

**Late Chunking：先在完整上下文中编码，再按照 Chunk 边界做 Pooling 得到每个 Chunk 的 Embedding**

这样做最大的好处就是，普通切分中每一个 Chunk 做 Embedding 的时候看不到其他 Chunk 的上下文，而 Late Chunking 中的 Token 已经在整段文本上下文中完成了编码，因此能够保留更多跨 Chunk 的上下文信息。

**不过 Late Chunking 仍然受到 Embedding 模型最大上下文长度的限制，所以并不是任意长度的文档都可以一次性全部放进去，而是在模型支持的上下文窗口范围内进行整体编码。**

## 五、怎么规避语义被切割掉的问题

第四个问题里面已经讲了其中的三个了：**固定切分 + overlap、语义切分、父子切分。**

剩下补充 3 个：

### 1. 句子窗口检索

这个重点不在于怎么切，重点在于检索后怎么返回。

为了弥补缺失的上下文信息，检索命中了之后，将这个句子的前后 N 个句子一起返回，给 LLM 一起阅读，弥补缺失的上下文信息。

比如原文：

```
句子1 → 句子2 → 句子3 → 句子4 → 句子5
```

检索的时候命中了 `句子3`，那么最终可以把：

```
句子2 + 句子3 + 句子4
```

一起返回给 LLM。

**这种方式的核心思想就是：小粒度负责检索，大一点的窗口负责给 LLM 补充上下文。这样既能保证检索的精准度，又能够避免单独一个句子缺少前后文的问题。**

------

### 2. 命题化切割

质量比较高，但是成本也比较高的一种方法，就是**将原始文本拆解或者改写成多个 Proposition（命题）。**

**命题不是单纯地按照句号把文本切成一句一句，而是把原文转换成多个“原子化、自包含”的事实表达。一个命题只表达一个相对独立的事实，并且包含理解这个事实所需要的上下文，这样即使脱离原文也能够被理解。**

比如原文：

> 马斯克创办了 SpaceX。这家公司在 2002 年成立，总部位于美国加州。

直接按句子切：

```
这家公司在 2002 年成立。
```

这里的“这家公司”脱离上下文之后，就不知道指的是谁。

命题化以后可以变成：

```
SpaceX 由马斯克创办。
SpaceX 成立于 2002 年。
SpaceX 总部位于美国加州。
```

**这样每一个命题都是一个原子化并且自包含的事实，可以直接作为检索单元进行 Embedding 和检索，不需要依赖原来相邻的句子才能理解。**

**这种方式通常需要使用 LLM 或专门的模型从原始文档中提取命题，因此文档预处理的成本会比较高；同时原始文档可能会被拆成大量命题，向量数量也会上升，所以存储和索引成本也会增加。**

------

### 3. Contextual Retrieval

Contextual Retrieval 是 Anthropic 提出的一种用于改善 RAG 检索效果的方法。

传统 RAG 中，chunk 块已经切分好了以后，会直接进行 Embedding：

```
原始 Chunk → Embedding
```

问题就是 Chunk 一旦脱离原文，可能会缺少必要的上下文。

比如一个 Chunk 只有：

```
该公司的收入相比上一季度增长了 3%。
```

单独拿出来根本不知道“该公司”是谁，也不知道是哪一年、哪个季度，所以进行 Embedding 和检索的时候可能很难正确召回。

Contextual Retrieval 的做法就是：**让 LLM 同时看到完整文档和当前 Chunk，然后根据整篇文档的信息，为当前 Chunk 生成一段简短的、Chunk 专属的背景信息，Anthropic 的实验中这个 Context 通常是 50～100 tokens。**

比如生成：

```
这段内容来自 ACME 公司 2023 年第二季度的 SEC 文件，讨论的是 ACME 公司 Q2 2023 的营收表现。
```

然后把：

```
背景信息 + 原始 Chunk
```

拼接起来：

```
这段内容来自 ACME 公司 2023 年第二季度的 SEC 文件，讨论的是 ACME 公司 Q2 2023 的营收表现。该公司的收入相比上一季度增长了 3%。
```

再进行 Embedding。

所以可以简单理解成：

```
完整文档 + 当前 Chunk → LLM → 生成 Chunk 的 Context
```

然后：

```
Context + Chunk → Embedding → 向量库
```

**而且 Anthropic 完整的 Contextual Retrieval 不只是 Contextual Embeddings，还包括 Contextual BM25：生成出来的 `Context + Chunk` 除了用于 Embedding，也会用于建立 BM25 索引。**

所以 Contextual Retrieval 的核心思想就是：

**Chunk 本身不够完整 → 根据全文给 Chunk 补充必要背景 → 再进行检索。**

**需要用到LLM进行生成的地方，会出现高成本问题，这个时候可以引入prompt cache，显著降低成本**

## 六、解释一下embedding，如何选择和评估一个embedding模型

首先解释什么是embedding：

Embedding 其实就是把一段文本转化为高维的向量，**这个向量可以表示文本的语义特征。基于 Embedding 的向量检索，本质上就是计算 Query 向量和文档向量之间的相似度，例如余弦相似度、点积等。通常语义越相似的文本，在向量空间中的距离也越近。**

常见的embedding模型主要有：
openai的：text-embedding

中文场景的有：bge

怎么选择一个embedding模型，我觉得主要是有以下几个方面考虑：

1. 中英文场景：看当前的知识库什么场景比较多，如果是中文场景比较多我会优先选择bge这种表现比较好的
2. 支持的维度：维度并不是越高，检索精度就一定越高。不同模型之间不能简单通过维度判断效果，例如一个优秀的 768 维模型完全可能超过另一个 1024 维模型。维度主要影响向量的信息容量以及存储、内存和检索计算成本。实际模型可能有 384、768、1024、1536、3072 等不同维度，需要在检索效果和成本之间进行权衡。
3. 支持输入的长度：**模型支持的最大输入长度决定了一次最多能够编码多少 Token，但并不意味着支持的长度越大，Chunk 就应该切得越大。Chunk 太大会混入过多无关语义，反而可能降低召回效果。所以 Chunk Size 应该根据文档结构和实际检索效果来确定，模型最大输入长度主要是一个上限约束。**
4. 还需要考虑模型的推理速度，成本和部署方式

如何评估一个embedding模型：
我认为评估这个模型不应该只看榜上最优的模型，最好是在自己知识库上准备几百个问题和答案，然后看hit@k指标（hit@3 = 0.8：检索到的80%的chunk块，前三条能命中答案），如果这个指标不行，那么再进行进一步排查

## 七、常见的几种 Embedding 算法

经历了三代，每代只记一个就行了。我感觉agent知识加上rag，记多了也记不住，之前看过一遍，现在有全忘了，没绷住

### 第一代（静态词向量）：Word2Vec

Word2Vec 给每一个词都生成一个向量，但是缺点是每一个词的向量都是固定的。

比如超市里卖的“苹果”和“苹果手机”的“苹果”，实际上语义完全不一样，但是 Word2Vec 生成的词向量是一样的，无法根据上下文动态改变词的表示。

### 第二代（上下文相关向量）：BERT

BERT 解决了第一代的问题，引入了 Transformer，**同一个词在不同上下文中可以得到不同的向量表示。**

但是又有一个缺点，**经典 BERT 在做句子相似度任务时，通常采用 Cross-Encoder 的方式：把两个句子拼接后一起输入 BERT，例如 `[CLS] 句子A [SEP] 句子B [SEP]`，然后直接计算两个句子的相关性。**

所以说，如果一个文档库有**上百万条文档**，每次检索都要把用户的问题分别和这上百万条文档进行拼接，再逐条跑一遍 BERT，计算成本非常高，**而且无法提前把文档编码成向量并建立向量索引进行快速检索。**

### 第三代（句子级向量 / 对比学习）：BGE

第三代解决了第二代的问题，如 BGE。做法是将两个独立的句子**分别输入 Embedding 模型，各自得到一个固定长度的句子级向量。文档的向量可以提前计算并存入向量数据库；检索时只需要计算 Query 的向量，再通过余弦相似度等方式寻找最相似的文档向量。**

**BGE 这类模型通常通过对比学习训练，让语义相近的句子向量更接近，让语义无关的句子向量距离更远。**

## 八、什么是向量数据库，有没有做过向量数据库的对比

向量数据库主要是用来存储和检索向量的数据库，它和一般传统的数据库是不一样的，因为一般传统的数据库，像mysql，大部分都是精确查找，主要通过字段值、索引等进行精确匹配或范围查询；而向量数据库主要解决的是高维向量的相似度检索，比如通过余弦相似度、欧氏距离、内积等方式，找出和查询向量最相似的 TopK 数据。语义检索本身的语义能力主要来自 Embedding 模型，向量数据库负责对生成的向量进行高效检索。

向量数据库的查找主要用了ANN算法，主流的ANN算法有两类：

- HNSW

  > 它本质上是一种**基于多层图的索引**。上层图比较稀疏，用来快速定位大概区域；越往下图越密集，用来进行更精细的查找，最终找到和目标向量比较接近的一批向量。它的优点是查询速度快、召回率高，缺点是构建索引比较慢，而且比较占内存。

- IVF

  > 这个是对向量先做一次聚类，然后从聚类里面进行查找。比如可以通过聚类把大量向量划分到不同的簇中。查询时先判断查询向量和哪些簇比较接近，然后只在这些簇里面继续搜索，而不是遍历全部向量，所以能够减少计算量。

常见的向量数据库：Chroma，Qdrant，Milvus这些，从左到右，规模越大，对于个人开发者来说Chroma完全足够够用了
