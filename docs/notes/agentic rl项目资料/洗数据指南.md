## 前言

洗数据一般是通过三步法：
**代码规则筛选-llm as judge-人工抽查**

## 一、首先先搞明白为什么洗数据

传统的后训练流程：**基模 → SFT → GRPO → 评测**

在sft这一步，主要是教给基模一些专家轨迹，更新模型参数，让模型学会在某一个状态下，下一步应该调用什么工具，传递什么参数

当然，如果模型在能力足够强大的情况下，可以直接跳过SFT，进行GRPO训练。但是如果模型能力比较薄弱，直接进行RL，会出现很多问题。

GRPO最忌讳的一个情况是，组里面要么全对，或者全错，如果上来进行GRPO，产生一堆垃圾Trajectory，实在是对算力资源的浪费。所以第一步需要对基模进行微调，将专家轨迹递交给基模训练，让基模学会在当前状态下，应该调用什么工具。

## 二、拿到一条轨迹后，我们如何将它洗干净？

### 1. 先决定整条要不要

程序先看环境结果：

- 如果最后的结果错误、只满足部分要求等情况，**整条Trajectory不进入SFT数据**
- 如果是完整、有效的 `结果`，继续检查中间实际执行的动作是否合法。
- 如果是评测集的题，或者这道题已经收过一条合格轨迹，也不再收。

### 2.在确定保留的轨迹里面，删掉一些可能会误导模型的信息

例子：

我要买一件s码的衣服 →搜索衣服 →返回商品A →打开商品A →商品A的衣服可选规格只有L码了 →这个规格不存在，不执行 →找另外一件衣服B →打开商品B →选择S码规格 →购买 →商品购买完成

上面这个例子只是帮助理解的，真实的生产环境应该会更严谨

可以看到，中间我们绕了几步，我们希望把绕路的这几步教会给模型，所以要进行删除

删除后是这样的：
我要买一件s码的衣服 →搜索衣服 →找衣服B →打开商品B →选择S码规格 →购买 →商品购买完成

### 3.去掉额外的信息

程序存在：

- 删除 `reasoning_content` 等私有推理字段和额外审计字段；

  > Teacher的回复会带着一堆reasoning_content
  >
  > reasoning_content：我先搜索，再看看商品材质……  ← 单独的推理字段
  > tool_calls：search_products({"query":"乳胶枕"}) ← 实际工具调用
  > 这些都要删除

- 保留正常的工具调用和环境观察；

  > 工具调用和调用的结果需要保留

- 将最后的购买工具回复统一换成“已完成”，去掉终局奖励信息。

  > 最后的回复简化，回复一个已完成即可
  >
  > 不需要：
  > 购买完成。
  > Reward: 1.0
  > reward_type: gold_purchase
  > reward_valid: true
  > ……

### 4.将清洗后的数据写进训练数据

原始轨迹raw.jsonl需要保留，方便检查，清洗后的对话写入SFT文件，再按任务划分验证集和数据集

### 5.总结

总体来说就是：

- 第一步：筛选轨迹，看看有哪些轨迹是成功的
- 第二步：成功的轨迹再进行整理，删掉多余的信息

## 三、具体怎么洗？（三步法）

假设用户要求：

> 帮我买一个乳胶枕，预算不超过 100 元。

Teacher 产生了三条轨迹：

| 轨迹 | 购物过程                                           | 最终结果           |
| ---- | -------------------------------------------------- | ------------------ |
| A    | 搜索 → 打开商品 → 买下 150 元的枕头                | 不满足预算         |
| B    | 搜索 → 打开商品 → 反复查看相同页面 → 选规格 → 购买 | 有效 gold_purchase |
| C    | 搜索 → 打开商品 → 核验材质、规格和最终价格 → 购买  | 有效 gold_purchase |

### 1.代码规则筛选-先看有没有问题

通过代码检查确定的事实

- 环境是否确认完整、有效的 `gold_purchase`；
- 执行有没有报错，轨迹有没有中途结束；
- 工具参数是否合法，点击目标是否出现在当前页面；
- 是否与评测题重叠，是否重复收录同一道题。

上面三条Trajectory中，A会被淘汰

### 2.LLM as judge

将通过第一轮筛选的Trajectory交给LLM，LLM需要看到用户的要求，每一步调用的工具，环境返回，审阅标准等

对于B、C这两条，B的第4~6步会出现相同的内容，送去人工复核，看看是不是绕路了。C没有冗余，适合作为专家Trajectory

**关键：**

**Judge 必须说明依据，不能只说这条不好。** 它的输出通常是评分、问题标签、证据位置和置信度；后续程序再按事先约定的规则决定保留、淘汰或送人工复核。Judge 不一定直接改写轨迹。

### 3.人工抽查

抽查覆盖类型：

- Judge 认为好的，检查有没有漏掉问题；

- Judge 建议淘汰的，检查有没有误删；

- Judge 不确定、代码标记可疑的，重点检查。

比如B：
LLM：反复查看相同的页面，疑似存在绕路

人工：打开对于的步骤，看看返回的内容

这个时候会出现两种情况：

1. 内容确实完全相同，绕路了，可以直接淘汰整条
2. 选择规格后，价格发生变化，需要从新核验，这个时候就需要保留

**在这里人工复核的原因就是怕很多长轨迹，搜索多的情况会被认为是坏数据**
