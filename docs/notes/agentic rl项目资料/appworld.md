## 一、这个appworld提供什么

### 1，提供了一个真实的appworld世界

实现了 9 个日常 App、457 个 API、100 多张数据库表，以及约 100 个虚拟用户的数字生活。Amazon、Spotify、Venmo、Gmail、Todoist、SimpleNote、Splitwise 等 App 之间还存在真实的状态联动。数据库和时间都可以 reset，所以同一个 Agent、不同 Agent 可以从完全相同的初始世界开始跑。
**注意：这里的API对应这APP的操作，一个api就是一个app的操作，比如说微信按钮点击的api，对应的就是微信单击按钮**

辅助：

- **API Docs**：相当于工具说明书，供 Agent 查询“有什么接口、参数怎么填”。

- **Supervisor**：相当于委托任务的人，提供其模拟账户、地址、支付卡等信息，以及提交任务完成的接口

### 2，AppWorld benchmark

| 数据集           | 场景类型数 | 具体任务数 | 用途                        |
| ---------------- | ---------- | ---------- | --------------------------- |
| `train`          | 30         | 90         | 训练、示例、开发            |
| `dev`            | 19         | 57         | 调试和选择方案              |
| `test_normal`    | 56         | 168        | 常规测试                    |
| `test_challenge` | 139        | 417        | 挑战测试（全新的app和任务） |
| **合计**         | **244**    | **732**    | 每类场景对应 3 道任务       |

一个有250个scenario，主要是单app的任务和跨app的任务训练，比如说在单个app上操作：打开音乐软件，播放我喜欢的歌单。跨app操作：我的备忘录里面存的还欠着我的钱的人，帮我在微信里面催他们还款

**最后的评分：**

分为了两个指标：

| 指标                | 含义                                       |
| ------------------- | ------------------------------------------ |
| **TGC：任务完成率** | 具体任务中，有多少道通过全部检查           |
| **SGC：场景完成率** | 同一场景的各道变体都成功，才算这个场景成功 |

现成 benchmark 已经规定了题目、初始环境和成功条件；Agent 自己决定怎么完成，评测程序检查最终结果及相关状态变化。过程日志能看，但过程效率和偶然成功需要额外分析。也就是是说，一个agent生成的一条Trajectory里面，如果说绕路了，有些前置条件没有检查，直接选择了某个确定的答案，这些情况下，AppWorld是分析不出来的。（我认为这里可以借鉴shop agent的思路，引入LLM as judge进行对轨迹的检查，因为这边都可以通过api的日志来进行分析，每一个操作都是有日志的）

## 二、这个appworld的创新点：该改的必须改，不该动的不能乱动

**保存任务开始前的数据库，再与结束后的数据库比较，把“哪里变了”逐项拿去检查。**

- **必须发生的变化**：例如让你买一件指定的衣服，就必须产生符合要求的订单。

- **允许发生、但不强制的变化**：例如下单后，购物车可以清空，也可以恢复成原来的内容。

agent在执行了之后，通过数据库的对比，能够看到表里面的哪些记录变化了

检查方式：

1. 看改动范围（播放音乐只能修改音乐的表，不能修改金钱的表）
2. 看改动数量和类型
3. 看修改后是否正确

**主要比较的是开始与结束之间留下的净变化。如果 Agent 中途乱改，最后又完全恢复，单靠前后状态比较通常看不出来；重复查询、绕路也未必留下数据库变化。这些仍然需要过程日志来评估。**
